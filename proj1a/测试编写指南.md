# 如何给 `LinkedListDeque61B` 写测试 —— 教学指南

> 面向 CS 61B Project 1A。读完你应该能自己写出覆盖全部 25 个 flag 的测试，
> 并且在测试失败时知道怎么定位。
>
> 配套文件：`tests/LinkedListDeque61BTest.java`

---

## 0. 先想清楚：测试到底在测什么

一条测试 = **给定一个状态 → 做一件事 → 检查结果是否符合预期**。

写测试本质上就是把你脑子里那句"这当然应该是对的呀"变成机器能自动检查的代码。
你自己跑十遍觉得没问题不算数，因为**人会漏、会累、会改代码而忘了重跑**。

合格的一条测试必须满足：

1. **能失败**：如果你的实现写错了，这条测试必须变红。
2. **失败时说得清**：红的时候，你能从消息里看出"期望什么、实际是什么"。
3. **只测一件事**：红的时候，你能立刻知道是哪个行为坏了。

第 1 条最容易被忽略。没有断言的测试永远绿，等于没写。

## 1. 工具：JUnit 5 + Truth

### 1.1 JUnit 5 —— 告诉 Java "这是一个测试"

```java
import org.junit.jupiter.api.Test;

@Test
public void myFirstTest() {
    // 这里写准备 / 执行 / 断言
}
```

- `@Test` 让这个方法能被测试框架发现并执行。
- 方法不能是 `private`、不能有返回值、不能有参数（习惯上写成 `public void`）。
- 在 IntelliJ 里，方法左边会有一个绿色三角，点它运行这一个测试；
  类名左边的绿色三角运行整个类。想调试就用旁边的 Debug（绿色虫子）。

### 1.2 Truth —— 写断言

本项目用 Google 的 Truth，不用 JUnit 自带的 `assertEquals`。原因：失败信息更清楚。

```java
import static com.google.common.truth.Truth.assertThat;
import static com.google.common.truth.Truth.assertWithMessage;
```

**最常用的几个：**

```java
assertThat(actual).isEqualTo(expected);   // 相等
assertThat(actual).isNull();              // 是 null
assertThat(actual).isNotNull();           // 不是 null
assertThat(flag).isTrue();                // 布尔为真
assertThat(flag).isFalse();               // 布尔为假

assertThat(list).isEmpty();               // 空列表
assertThat(list).hasSize(3);              // 大小为 3
assertThat(list).containsExactly("a", "b").inOrder();  // 元素和顺序都完全一致
assertThat(list).containsExactlyElementsIn(other).inOrder();
assertThat(list).contains(2);             // 包含某元素
```

**想给失败信息加说明时**，用 `assertWithMessage`：

```java
assertWithMessage("删掉 3 个元素后 size 应该归零")
    .that(d.size())
    .isEqualTo(0);
```

失败时会打印你自己写的那句话，比 `expected 0 but was 1` 有用得多。

## 2. 写一条测试的五个步骤

以 `removeFirst` 为例，把思考过程摊开：

```java
@Test
public void removeFirstReturnsFrontAndShrinksList() {
    // ① 准备（Arrange）：造一个你完全知道长什么样的状态
    Deque61B<String> d = new LinkedListDeque61B<>();
    d.addLast("a");
    d.addLast("b");
    d.addLast("c");          // 现在一定是 [a, b, c]

    // ② 执行（Act）：只做一件想验证的事
    String removed = d.removeFirst();

    // ③ 断言（Assert）：检查【返回值】
    assertThat(removed).isEqualTo("a");

    // ④ 断言：检查【状态】—— 这一步最容易被新手漏掉
    assertThat(d.toList()).containsExactly("b", "c").inOrder();
    assertThat(d.size()).isEqualTo(2);
}
```

**为什么"返回值"和"状态"要分开断言？**
一个常见 bug 是：返回值对了，但链表没真的删掉（`sentinel.next` 还指着旧节点）；
或者删掉了，但返回的是错的那个。只查一面，另一面的 bug 就藏过去了。

**第 ⑤ 步是心态**：先跑，确认它是**红的**。绿着跑通的测试说明不了任何事。

## 3. 场景清单法：把"覆盖全面"变成可执行列表

"全面"不是感觉，是**维度枚举**。对 deque 来说，主要就三个维度：

### 3.1 通用模板

| 维度 | 取值 |
| --- | --- |
| 当前状态 | 空 / 1 个 / 2 个 / 多个 |
| 操作 | addFirst / addLast / removeFirst / removeLast / get / getRecursive / size / isEmpty / toList |
| 参数或位置 | 合法首 / 合法中 / 合法尾 / 负索引 / 超大索引 |

每个组合只要**有意义**就写一条。比如：

- `addFirst` × 空表 → `add_first_from_empty`
- `addFirst` × 非空 → `add_first_nonempty`
- `removeFirst` × 空表 → 应该返回 `null`，不能崩
- `get` × 负索引 → 应该返回 `null`，不能反向遍历
- `remove` 到只剩 1 个 → 指针最容易出错的地方

### 3.2 本项目的 25 个 flag

评分用的覆盖率清单（官方 `flags` 页），也是你的测试目标：

**add（4）**：`add_first_from_empty`、`add_last_from_empty`、
`add_first_nonempty`、`add_last_nonempty`

**add after remove（2）**：`add_first_after_remove_to_empty`、`add_last_after_remove_to_empty`

**remove（6）**：`remove_first`、`remove_last`、`remove_first_to_empty`、
`remove_last_to_empty`、`remove_first_to_one`、`remove_last_to_one`

**get（6）**：`get_valid`、`get_oob_large`、`get_oob_neg`、
`get_recursive_valid`、`get_recursive_oob_large`、`get_recursive_oob_neg`

**size（3）**：`size`、`size_after_remove_to_empty`、`size_after_remove_from_empty`

**isEmpty（2）**：`is_empty_true`、`is_empty_false`

**toList（2）**：`to_list_empty`、`to_list_nonempty`

写法上的小技巧：**一条测试里把"场景"做足，但断言围绕同一个行为**。
比如 `add_first_after_remove_to_empty` 必须真的走到"删空后再加"这个路径，
不能只是"新建一个空 deque 然后 addFirst"——那是另一个 flag。

## 4. 怎么选断言

### 原则一：能查结果，就不要只查"没崩"

```java
// 差：只要不抛异常就过，几乎什么都测不出来
d.removeFirst();

// 好：明确检查删掉的是谁
assertThat(d.removeFirst()).isEqualTo("a");
```

### 原则二：具体值 > 笼统判断

```java
// 差
assertThat(d.toList()).isNotNull();

// 好
assertThat(d.toList()).containsExactly("a", "b", "c").inOrder();
```

`containsExactly(...).inOrder()` 相当于同时检查了三件事：元素集合、数量、顺序。

### 原则三：布尔断言别忘 `.isTrue()`

```java
// 差：这个断言等于没写！它只检查"返回了一个 boolean"
assertThat(d.isEmpty());

// 好
assertThat(d.isEmpty()).isTrue();
```

### 原则四：一条测试里别塞太多不相关的断言

断言越多越全面，但失败时越难定位。折中：
**一条测试围绕一个方法/行为，断言它的返回值 + 它造成的状态变化。**

## 5. 五个常见错误

### 5.1 忘了写断言

```java
@Test
public void addFirstTest() {
    Deque61B<String> d = new LinkedListDeque61B<>();
    d.addFirst("a");          // 没有 assertThat，永远是绿的
}
```

### 5.2 布尔断言没加 `isTrue()` / `isFalse()`

见上面第 4 节原则三。

### 5.3 只测正常路径

真实的 bug 几乎都出在：空表、只剩一个元素、越界下标、连续增删。

### 5.4 用还没验证的方法去验证别的方法

```java
// 危险：toList 自己可能有 bug，
// addFirst 的 bug 和 toList 的 bug 有可能互相抵消，让你误以为都对了
assertThat(d.toList()).containsExactly("a").inOrder();
```

**这不是说不该用 `toList`** —— 它确实是最方便的观察窗口（本项目的骨架测试也这么写）。
而是说：如果你怀疑 `toList` 本身有问题，就要换一种方式验证（比如 `size()`、`get(0)`），
或者先把 `toList` 单独测通，再用它去测别的。

### 5.5 测试之间共享状态

```java
static Deque61B<String> shared = new LinkedListDeque61B<>(); // 别这样
```

每条测试都应该自己 `new` 一个对象。共享状态会让"单独跑通过、一起跑失败"这种诡异问题缠上你。

## 6. 覆盖率检查器到底在干什么

评分器会拿**你写的测试**去跑**官方的正确实现**，看你的测试能触发到哪些场景，
从而判断你的测试"想没想到了"这些情况。

含义有三点：

1. 评分跑的是**官方正确实现**，不是你现在这份（可能还没写完的）代码。所以你的测试必须能通过正确实现；连官方实现都跑不过，说明是测试写错了。
2. 覆盖率看的是你对 deque **做了**哪些操作（命中了哪些场景），**不看**你在断言里写了什么。所以没有断言的测试也可能“被算作覆盖”——但它永远绿、抓不到 bug，别指望它。
3. 覆盖率不等于正确性。没覆盖到的场景，你的测试再多也可能漏。

## 7. 测试失败了怎么查

按这个顺序，别乱猜：

1. **读失败信息**。Truth 会说 `expected: ... but was: ...`，先看这两个值是不是你预期的。
2. **判断是"实现错"还是"测试错"**。对着 spec 和接口 javadoc 读一遍你的测试。
3. **打断点**。在测试里"执行"那一步之前下断点，Debug 运行，
   用 Step Over（F8）一行行走，看 `sentinel.next`、`sentinel.prev` 这些字段怎么变。
4. **二分法**。一条测试断言太多时，注释掉下半部分，先确认上半部分哪一句开始红。
5. **回到最小例子**。如果 `[a, b, c]` 的情况有问题，先试 `[a]`，再试 `[a, b]`。

调试时最有用的一句话：**程序现在真实的状态是什么**，而不是**我以为它是什么**。

## 8. 链表特有的坑（写测试时重点关注）

| 坑 | 测试怎么写才能抓到 |
| --- | --- |
| 空表时 `sentinel.next == sentinel`，不是 `null` | 空表上 addFirst / addLast / get |
| 删掉最后一个元素后，`sentinel` 没指回自己 | 删到空，然后再 add |
| 只剩 1 个元素时删除逻辑走错分支 | `remove_*_to_one`、`remove_*_to_empty` |
| 首尾指针没同时更新 | 交替 addFirst / addLast 后 `toList` 检查顺序 |
| `get` 负数下标被当成"从头没走"返回首元素 | `get(-1)` 必须是 `null` |
| 删除后没断引用，节点仍被链住（内存问题） | 删到空后 `isEmpty()` 为 true、`size()` 为 0 |

## 9. 提交前自查清单

- [ ] 每个 `public` 方法都至少有一条测试
- [ ] 空表场景都测了（每个操作）
- [ ] 单元素场景都测了
- [ ] 越界 / 非法参数都测了（负索引、超大索引、空表删除）
- [ ] 每条测试都**有**断言，且断言的是**具体值**
- [ ] 布尔断言都加了 `.isTrue()` / `.isFalse()`
- [ ] 每条测试自己 `new` 对象，不共享状态
- [ ] 测试名能让人一眼看出测的是什么
- [ ] 写完后先跑一遍，确认在没实现时是**红的**（TDD 的"红"）

## 10. 练习

1. 给 `removeFirst` 写一条**单元素**场景的测试：只有 `["a"]`，删完必须 `isEmpty()` 为 `true`。
2. 写一条测试验证：`addFirst("x")` 之后，`get(0)` 必须等于 `"x"`（不看 `toList`，只用 `get`）。
3. 写一条测试验证：连续 `addLast(1..5)` 再 `removeLast()` 三次，`toList()` 必须是 `[1, 2]`。
4. 故意把你实现里的 `addFirst` 改错（比如少更新一个指针），跑测试，看有哪几条变红。
   这能训练你判断"测试抓不抓得住 bug"。

## 附：一条好测试长什么样

```java
@Test
public void removeFirstToEmptyTest() {
    // 准备：造一个 3 元素的 deque
    Deque61B<Integer> d = new LinkedListDeque61B<>();
    d.addLast(1);
    d.addLast(2);
    d.addLast(3);

    // 执行 + 断言：一步步删，最后一步才是重点（删空）
    assertThat(d.removeFirst()).isEqualTo(1);
    assertThat(d.removeFirst()).isEqualTo(2);
    assertThat(d.isEmpty()).isFalse();          // 中间状态也要查

    assertThat(d.removeFirst()).isEqualTo(3);   // 删空
    assertThat(d.isEmpty()).isTrue();
    assertThat(d.size()).isEqualTo(0);
    assertThat(d.toList()).isEmpty();
}
```

它好在哪里：场景命名清楚、断言具体、覆盖了"删一半"和"删空"两个关键状态。
